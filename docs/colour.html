Game Boy Color

Adding CGB support while keeping full DMG accuracy — Phases 0–2: model plumbing, banked memory and colour rendering (in progress)

Design Decision — DMG Stays, Model Is Chosen at Boot

DMG support is kept permanently. The Blargg DMG regression suite (cpu_instrs, instr_timing, mem_timing, mem_timing-2, oam_bug, dmg_sound) is the accuracy baseline established while building the CPU, bus timing, OAM bug and APU quirks. Dropping DMG would discard it.

The model is selected at boot and cannot be hot-swapped, matching SameBoy, BGB and mGBA. The model determines boot register values, palette RAM contents, OAM-bug presence and PPU behaviour, so changing it mid-run is meaningless — it requires a full machine reset.

Phase 0 — Knowing Which Machine We Are

The first two steps change nothing about rendering or timing. They only establish which hardware model is being emulated and what the machine looks like right after the (skipped) boot ROM. Every Blargg result must stay identical.

Detecting the Cartridge

Header byte $0143 is the CGB flag:

ValueMeaning
$80CGB-enhanced — runs on both DMG and CGB
$C0CGB-only
anything elseDMG cartridge; a real CGB runs it in DMG-compat mode

Memory::load_rom() reads it next to the other header bytes ($0147, $0148, $0149) and stores it in a new cgb_flag member: 

constexpr uint16_t ROM_HEADER_CGB_FLAG = 0x0143; // constants.h

cgb_flag = rom[ROM_HEADER_CGB_FLAG];             // Memory::load_rom

Model State

enum class Model { DMG, CGB };

// on GameBoy:
Model requested_model = Model::DMG; // what the user asked for
bool  model_is_auto   = true;
Model model           = Model::DMG; // resolved at load_rom time
bool  cgb_mode        = false;      // model == Model::CGB
bool  dmg_compat      = false;      // CGB hardware running a DMG cartridge

dmg_compat is a sub-mode of CGB, not a third Model value. A DMG-compat machine is CGB hardware — it has banked VRAM/WRAM, palette RAM and double speed — it just renders a DMG game through a colourised palette. 

void GameBoy::set_cartridge_mode()
{
    bool cart_is_cgb = (memory.cgb_flag == 0x80 || memory.cgb_flag == 0xC0);
    model      = model_is_auto ? (cart_is_cgb ? Model::CGB : Model::DMG) : requested_model;
    cgb_mode   = (model == Model::CGB);
    dmg_compat = (cgb_mode && !cart_is_cgb);
}

The Ordering Trap

The emulator doesn't run a boot ROM, so reset() used to hand-write the post-boot state. But that state depends on the model, and the model isn't known until the ROM header has been parsed — which happens after reset(). Setting a CGB-specific value in reset() would always see cgb_mode == false.

The fix is to split the work into three steps and call them in order from load_rom():

void GameBoy::load_rom(const std::vector<uint8_t>& rom, const std::string& rom_path)
{
    reset();                  // clear state, relink pointers
    memory.load_rom(rom);     // parses the header, fills cgb_flag
    set_cartridge_mode();     // resolve model / cgb_mode / dmg_compat
    apply_post_boot_state();  // now model-specific values can be applied
    memory.load_battery(rom_path);
}

One more subtlety: reset() must not touch model_is_auto or requested_model. They are set from the command line before load_rom() is called, so resetting them would silently discard --model. Only the resolved model, cgb_mode and dmg_compat are cleared, since set_cartridge_mode() recomputes them. Consequently reset() no longer applies post-boot state by itself — a standalone reset (a hotkey, later) has to call apply_post_boot_state() too.

Command Line

The model can be forced from the command line; auto is the default:

gbemu.exe <rom> [--disassemble|-d] [--headless] [--model=auto|dmg|cgb]

An unrecognised value is rejected with an error rather than falling back to a default. After loading, the resolved model, cgb_mode and dmg_compat are printed, which is the quickest way to confirm detection: a DMG ROM run with --model=cgb should report CGB mode: Yes and DMG compatibility mode: Yes.

Post-Boot State per Model

A real boot ROM leaves the CPU registers and several I/O registers in model-specific states before handing control to the cartridge at $0100. The CPU constructor still initialises the DMG values; apply_post_boot_state() overrides them when cgb_mode is set.

CPU Registers

RegisterDMGCGB
AF$01B0$1180
BC$0013$0000
DE$00D8$FF56

A == $11 is the CGB detection contract. Every CGB game reads A at entry and takes its monochrome code path if it isn't $11. Getting this wrong makes a CGB ROM boot, run and render in greyscale with none of the colour code ever executing — a failure that looks like a PPU bug. B bit 0 distinguishes CGB (0) from GBA (1); it is not a DMG-compat flag. We emulate a CGB, so B = $00.

BG Palette RAM

The only storage added in this phase is the BG palette RAM array in Memory: 8 palettes × 4 colours × 2 bytes. Palette RAM isn't mapped into the address space; it is only reachable through the index/data register pairs, which arrive with palette support. 

uint8_t bg_palette_ram[64] = {}; // memory.h

Memory is zero-initialised on reset, and zero decodes to black, so the boot ROM's behaviour has to be applied explicitly. Colours are RGB555 (little-endian, bit 15 ignored), so filling every byte with $FF gives $7FFF, which is white. OBJ palette RAM needs no setup because real hardware leaves it undefined.

Why write_io_raw and Not write

Those post-boot values are read-back values, not values a game would write. Going through the normal bus write would be wrong once the registers get side effects: writing $FF to VBK would select VRAM bank 1 (value & 1), and writing $FF to HDMA5 has bit 7 set with a length of $7F, which would start an HBlank DMA. write_io_raw stores the byte straight into the register file with no side effects. As each feature lands and gets a real member (vram_bank, wram_bank, double_speed, hdma_active), the member's default already matches the post-boot value and the raw write can be dropped.

Phase 1 — Banked Memory

CGB doubles both RAMs: 16 KiB of VRAM as two 8 KiB banks (VBK, $FF4F) and 32 KiB of WRAM as eight 4 KiB banks (SVBK, $FF70). On DMG the same code paths must behave exactly as before.

VRAM Banking

Both banks hold tile data at $8000–$97FF; bank 1's $9800–$9FFF will later hold tile map attributes instead of tile indices. The interesting part is who reads which bank, so the accessors are split:

  • CPU bus — reads and writes go through the currently selected bank: read_vram_bank(addr, vram_bank).
  • PPU — keeps read_vram(addr), now defined as bank 0. Later the PPU will fetch a tile index from bank 0 and its attribute from bank 1 in the same operation, regardless of what VBK says, so it needs to name the bank explicitly.
uint8_t Memory::read_vram(uint16_t addr) const              // PPU, bank 0
{
    return read_vram_bank(addr, 0);
}

// Memory::read, $8000-$9FFF: CPU follows VBK
return read_vram_bank(addr, vram_bank);

A trap worth remembering: the bus read used to call read_vram() directly. Redefining that accessor as bank 0 silently pins every CPU read to bank 0 unless the bus read is re-pointed. Writes index vram[vram_bank * 0x2000 + …] directly, so they were unaffected.

The register is virtual: reads return vram_bank | 0xFE and writes store value & 1, both gated on cgb_mode. On DMG the address falls through to the generic register file, like any other unmapped register. Because of this, the post-boot value ($FE, bank 0) needs no explicit initialisation, and the C2 raw write for VBK is gone.

WRAM Banking

$C000–$CFFF is always bank 0; $D000–$DFFF selects banks 1–7, and writing 0 to SVBK selects bank 1. Echo RAM mirrors $C000–$DDFF, so it has to follow the selected bank too. Four places index wram (read and write for the main range, read and write for Echo RAM), and they previously used different base subtractions, so they now share one helper: 

uint32_t Memory::wram_offset(uint16_t addr) const {
    if (addr >= 0xE000) addr -= 0x2000;          // fold Echo RAM onto $C000-$DDFF
    if (addr < 0xD000) return addr - 0xC000;     // fixed bank 0
    return wram_bank * 0x1000 + (addr - 0xD000); // banked
}

wram_bank defaults to 1, which makes the CGB layout with bank 1 selected identical to the flat DMG mapping — that is why bank 0 must alias to bank 1. It also means a mistake in this helper can hide behind a green DMG regression: an early version had the $D000 comparison inverted, and the DMG results were unchanged only because the banked formula cancels out when wram_bank == 1. The DMG suites can't verify this commit; only a CGB check can (distinct values at $D000 under banks 1 and 2, bank 0 reading as bank 1, Echo RAM following the bank).

SVBK reads return wram_bank | 0xF8 and writes store value & 7 (0 becomes 1), gated on cgb_mode. As with VBK, the post-boot value comes for free from the member default, so its raw write can also be removed.

Verification

DMG regression unchanged: all Blargg suites match their previous results, with dmg_sound still 11/12 (test 10 is a known open failure).

Phase 2 — Colour Rendering

Phase 2 turns the PPU from a 2-bit-shade renderer into one that can produce CGB colour. It is five steps that have to land in order: a renderer refactor with no visible change, palette RAM, background attributes, sprite attributes, and finally the CGB rule for which of the two wins when a sprite and a background pixel overlap. Every step keeps the DMG path byte-for-byte identical.

Throughout, native CGB means cgb_mode && !dmg_compat. A DMG cartridge on CGB hardware (dmg_compat) has no attribute bytes and no per-sprite palette bits, so it keeps the DMG rules and only swaps the shade table for a palette in CRAM. The PPU holds its own copies of cgb_mode and dmg_compat, set by set_cartridge_mode(), so it needs no dependency on GameBoy.

Reference: Pandocs — Palettes, Tile Maps, OAM

A Per-Pixel RGBA Renderer

render_scanline() used to write a post-BGP palette index (0–3) into a framebuffer, and update_rgba_buffer() expanded the whole frame through GB_PALETTE_RGBA32[] at VBlank. That is a dead end for CGB: its pixels come from a 32768 colour space, so there is no 2-bit index to store. The renderer now writes a packed uint32_t straight into rgba_buffer for every pixel, and framebuffer and update_rgba_buffer() are gone (which also removes a 23,040-iteration pass per frame). Three places write pixels: the LCD-off fill, the BG-disabled line, and the main per-pixel write.

A Latent DMG Bug

While doing this, the sprite-behind-background test turned out to compare the wrong value. A sprite with the priority bit set shows through only where the background's raw colour ID is 0, but the code tested the shade that BGP maps that ID to. The two coincide for the usual BGP = $E4, which is why it never showed. A game that remaps BGP — a fade to white ($00) or an inverted screen — would have put every priority sprite in front of the whole background. The fix is to keep the raw ID in a local and test that. CGB priority needs the raw ID as well, so this was a prerequisite: 

uint8_t bg_color_id = ((byte2 >> bit_pos) & 1) << 1 | ((byte1 >> bit_pos) & 1); // raw, pre-palette
bool    bg_attr_priority = cached_tile_bytes.attr & 0x80;                                    // CGB only
uint8_t bg_color = (bgp >> (bg_color_id * 2)) & 0x03;                                      // DMG shade

Background and sprite resolution happen in the same per-pixel loop, so locals are enough; no extra line buffer is needed.

CGB Palette RAM

Colour palette RAM (CRAM) is two independent 64-byte banks: 8 palettes × 4 colours × 2 bytes, one for the background and one for objects. It is not in the address space; each bank is reached through an index register and a data register:

RegisterAddressRole
BGPI$FF68BG index: bits 0–5 byte address, bit 7 auto-increment
BGPD$FF69BG data: the byte at the current index
OBPI$FF6AOBJ index
OBPD$FF6BOBJ data

Three rules are easy to get wrong:

  • Reads of the data register never auto-increment; only writes do.
  • The index wraps from 63 back to 0 rather than saturating.
  • On hardware the increment still happens when a write is ignored during mode 3. The mode-3 lock is not emulated yet, so every write lands.

The index registers read back with bit 6 set (value | $40). All four branches are gated on cgb_mode; on DMG they fall through to the generic register file.

Colour Format and Correction

A colour is RGB555, little-endian, low byte first; bit 15 is ignored. Expanding with a plain x << 3 looks wrong on a modern display, because the CGB panel is unlit (maximum intensity is light grey), non-linear, and its pigments bleed into each other. The default is the usual correction curve: 

uint8_t r = (r5 * 13 + g5 *  2 + b5     ) >> 1;
uint8_t g = (g5 *  3 + b5              ) << 1;
uint8_t b = (r5 *  3 + g5 *  2 + b5 * 11) >> 1;   // 31,31,31 -> 248,248,248

color_correction selects the raw x << 3 expansion instead.

Who Owns What

The storage is split by what each side is responsible for. Memory owns the CRAM bytes, the index registers and the bus decoding. The PPU owns everything video-related: bg_palette_rgba[32] and obj_palette_rgba[32] (the converted colours), color_correction, and the conversion itself. Running the arithmetic per pixel would be wasteful, so a data write recomputes only the one affected entry, and rendering is a single array lookup, the same cost as the DMG path: 

// Memory::write, BGPD
uint8_t idx    = bcps & 0x3F;
bg_palette_ram[idx] = value;
int colour     = idx >> 1;
uint16_t rgb555 = bg_palette_ram[colour * 2] | (bg_palette_ram[colour * 2 + 1] << 8);
gameboy->ppu.update_palette_color(false, colour, rgb555);
if (bcps & 0x80) bcps = 0x80 | ((idx + 1) & 0x3F);

Two details matter here. The colour is rebuilt from both bytes of its pair: an early version read the high byte as ram[idx | 1], which for an odd index is the same byte as ram[idx], so every second write produced a wrong colour. And the cache has to be filled once at post-boot: BG CRAM starts as all $FF (white), but the cache starts zeroed, so apply_post_boot_state() calls ppu.rebuild_palette_cache(memory) after the fill, otherwise a CGB game shows black until it programs every palette.

Background and Window Attributes

In CGB mode every tile-map entry has an attribute byte at the same address in VRAM bank 1. The attribute at 1:9800 describes the tile named at 0:9800, so the same tile graphic used twice can have two palettes.

BitMeaning
7BG-to-OBJ priority: colour IDs 1–3 draw over objects
6Y flip
5X flip
4unused
3tile data VRAM bank
2–0BG palette 0–7

TileBytes gained an attr field, and fetch_tile_row() fills it. Because the attribute lives inside the struct the per-line tile cache already holds, it is cached together with the tile bytes for free; keeping it separately is how you get the classic bug of correct pixels with the previous tile's palette. The tile index always comes from bank 0, the attribute from bank 1, and the tile row from whichever bank the attribute selects: 

uint8_t attr = (cgb_mode && !dmg_compat) ? memory.read_vram_bank(tile_map_addr, 1) : 0;
uint8_t bank = (attr >> 3) & 1;
if (attr & 0x40) tile_pixel_y = 7 - tile_pixel_y;           // Y flip
row_bytes.byte1 = memory.read_vram_bank(tile_row_addr,     bank);
row_bytes.byte2 = memory.read_vram_bank(tile_row_addr + 1, bank);
row_bytes.attr  = attr;

X flip is applied at pixel extraction by inverting the bit position. Flips are per tile, so a flipped tile mirrors within its own eight pixels.

Colour Lookup

if (!cgb_mode)       bg_rgba = GB_PALETTE_RGBA32[bg_color];                 // DMG: shade via BGP
else if (dmg_compat) bg_rgba = bg_palette_rgba[bg_color];                   // BGP picks within palette 0
else                 bg_rgba = bg_palette_rgba[((attr & 0x07) << 2) | bg_color_id];

The middle branch exists because a DMG game on CGB has attr == 0. The native formula would then index by raw colour ID and ignore BGP, so fades and inverted screens would render wrongly. On real hardware, BGP, OBP0 and OBP1 index into CRAM in this mode.

Object Attributes and Priority Mode

The OAM attribute byte is reinterpreted on native CGB:

6Y flipY flip
5X flipX flip
4OBP0 / OBP1ignored

DMG games leave bits 3 and 2–0 as junk, so they are honoured only on native CGB. fetch_sprite_row() picks its VRAM bank from bit 3 under the same gate; the bank applies to both tiles of an 8×16 sprite.

The Sprite Line Buffer Carries Finished Colour

sprite_line used to hold a post-OBP shade, which cannot represent a CGB colour. A SpritePixel now holds the resolved RGBA and the whole attribute byte, and the sprite loop resolves the colour where the raw colour ID is known: 

struct SpritePixel { uint32_t rgba; uint8_t attributes; bool present = false; };

uint32_t rgba;
if (!cgb_mode)
    rgba = GB_PALETTE_RGBA32[(palette >> (color_id * 2)) & 3];
else if (dmg_compat)   // OBP picks the shade; OAM bit 4 picks OBJ palette 0 or 1
    rgba = obj_palette_rgba[((attr & SPRITE_PALETTE) ? 4 : 0) + ((palette >> (color_id * 2)) & 3)];
else
    rgba = obj_palette_rgba[((attr & 0x07) << 2) | color_id];
sprite_line[px] = { rgba, sprite.attributes, true };

The raw colour ID is not stored: a pixel is only written when it is non-zero, so "the object's colour ID is 0" is already handled by skipping it. The per-pixel resolve then reads present, rgba and attributes directly.

OPRI: Who Wins Between Two Sprites

DMG orders overlapping sprites by X coordinate, then OAM index. CGB orders purely by OAM position. OPRI ($FF6C) bit 0 selects the rule: 0 is CGB order, 1 is DMG order. scan_oam() already collects sprites in ascending OAM index, so CGB ordering is simply skipping the sort. The 10-sprites-per-line limit and the first-writer-wins rule are unaffected: 

bool dmg_priority = !cgb_mode || (memory.read_io_raw(IO_OPRI) & 1);
if (dmg_priority) std::sort(...);

The CGB boot ROM sets OPRI to 1 for DMG cartridges, so apply_post_boot_state() now writes dmg_compat ? 1 : 0 instead of a constant 0. Without that, a DMG game forced onto CGB would get OAM-order priority.

Background-to-Object Priority

On DMG, LCDC bit 0 enables the background and window; clearing it blanks them. On CGB it becomes a master priority flag: the background is still drawn but loses all priority, and objects always win. The "blank the line" early-out in render_scanline() therefore applies only to DMG and compat mode. In native CGB the winner is decided by an ordered set of tests:

  1. If the object's colour ID is 0, the background wins (already handled: such pixels are never stored).
  2. Else if LCDC bit 0 is clear, the object wins.
  3. Else if both the BG attribute's bit 7 and the OAM attribute's bit 7 are clear, the object wins.
  4. Else the background wins if its colour ID is 1–3; otherwise the object wins.
if (cgb_mode && !dmg_compat) {
    if (!sprite_present)                                         final_rgba = bg_rgba;
    else if (!(lcdc & LCDC_BG_ENABLE))                           final_rgba = sprite_rgba;
    else if (!bg_attr_priority && !(sprite_attr & SPRITE_PRIORITY)) final_rgba = sprite_rgba;
    else                                                         final_rgba = (bg_color_id == 0) ? sprite_rgba : bg_rgba;
}

Two sign traps: the OAM bit grants object priority when it is clear, not set; and the BG attribute bit wins even when the OAM bit says the object should be in front. The original DMG block is untouched behind the else.

Verification

DMG regression unchanged, run with --model=dmg: cpu_instrs, instr_timing, mem_timing and mem_timing-2 pass, oam_bug is 8/8, and dmg_sound is still 11/12 (test 10 is a known open failure). Tetris was checked by eye in DMG mode after the sprite changes.

Those suites only exercise the DMG path, so they say nothing about the CGB branches. Those have not yet been checked against a CGB ROM; cgb-acid2 covers attributes, palettes, sprite ordering and priority in a single image, and MagenTests has a ROM for the priority table. A DMG cartridge forced onto CGB shows a blank white screen for now, because BG CRAM starts all white and nothing installs a compatibility palette yet.
