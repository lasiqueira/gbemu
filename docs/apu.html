Audio Processing Unit (APU)

Implementing four-channel audio output for music and sound effects

Digital Audio Basics

Sound is produced by variations in air pressure. A sound wave has two key properties: frequency (how fast the pressure oscillates, measured in Hz — determines pitch) and amplitude (how large the oscillations are — determines volume). Humans can hear roughly 20 Hz to 20,000 Hz.

In a computer, audio is represented as a sequence of samples — periodic measurements of amplitude stored as integers. The Game Boy itself generates analog waveforms through its hardware; the emulator must capture this output digitally and send it to the host system's audio device.

  • Sample rate: samples per second. The emulator uses 44,100 Hz (CD quality).
  • Bit depth: precision of each sample. The emulator uses 16-bit signed integers (−32,768 to 32,767).
  • Stereo: two channels (left and right) sampled simultaneously.

Every 1/44,100 of a second (~22.7 µs), the emulator writes one left sample and one right sample to an output buffer, which SDL then feeds to the audio device.

APU Overview

The Game Boy APU has four independent sound channels, each with its own timbre, frequency, volume, and lifetime controls. Three registers govern the overall audio output:

RegisterAddressPurpose
NR520xFF26Master power switch; channel enable flags (read-only)
NR510xFF25Stereo panning — 8 bits, one per (channel × side)
NR500xFF24Master volume — 3 bits per side (value + 1 = 1–8×)

Powering off the APU (NR52 bit 7 = 0) resets all four channels to their default state and clears all channel registers.

Period Timer — Generating Frequency

All channels use a period timer that counts down in CPU cycles. When it reaches zero or below, it reloads and advances the channel's waveform position by one step:

ChannelTimer reloadWaveform step
CH1 / CH2(2048 − period) × 4duty_pos = (duty_pos + 1) & 7
CH3(2048 − period) × 2wave_pos = (wave_pos + 1) & 31
CH4(div == 0 ? 8 : div × 16) << shiftClock LFSR once

The period register is 11 bits (0–2047). A higher period value means fewer reloads per second, meaning a lower frequency. For CH1/CH2, the formula is: 

frequency (Hz) = 131072 / (2048 − period)

The 131,072 comes from: 4,194,304 (CPU Hz) ÷ 4 (timer multiplier) ÷ 8 (duty positions per period) = 131,072. CH3 uses a ×2 multiplier with 32 waveform positions, giving 65,536 / (2048 − period) Hz — one octave lower than CH1/CH2 at the same register value.

The timer uses += on each reload (not a hard reset), so sub-cycle remainders are preserved and the pitch remains accurate even when cycles are consumed in variable-size steps.

Reference: Pandocs — Period registers

Channel 1 — Square Wave with Sweep (NR10–NR14)

A square wave alternates between a high (loud) and low (silent) state at a fixed frequency. The fraction of time spent high is the duty cycle. The Game Boy supports four duty cycle values, stored as 8-bit bitmasks — each bit corresponds to one of the 8 positions in a single period:

duty_pos steps 0→7 on each period reload. The bit at that position in the duty table determines the output: 

static constexpr uint8_t DUTY_TABLE[4] = {
    0b00000001, // 12.5%
    0b00000011, // 25%
    0b00001111, // 50%
    0b11111100  // 75%
};

bool high = (DUTY_TABLE[duty] >> duty_pos) & 1;
return high ? envelope.current_vol : 0;

Channel 1 also has a frequency sweep — see the Frequency Sweep section.

Reference: Pandocs — Channel 1 registers (NR10–NR14)

Channel 2 — Square Wave (NR21–NR24)

Identical to Channel 1 in every respect except it has no NR10 sweep register. The same duty table, period timer, envelope, and length counter apply. It simply cannot change its own frequency autonomously.

Reference: Pandocs — Channel 2 registers (NR21–NR24)

Channel 3 — Wave Channel (NR30–NR34)

Instead of a fixed duty cycle, Channel 3 plays a custom 32-nibble (4-bit) waveform stored in Wave RAM (0xFF30–0xFF3F). Each of the 16 bytes holds two nibbles: 

0xFF30: [nibble 0][nibble 1]
0xFF31: [nibble 2][nibble 3]
  ...
0xFF3F: [nibble 30][nibble 31]

wave_pos advances 0→31 on each period reload. The current nibble is read as: 

uint8_t wave_byte   = wave_ram[wave_pos >> 1];
uint8_t sample_nibble = (wave_pos & 1) ? (wave_byte & 0x0F) : (wave_byte >> 4);

The ×2 timer multiplier (vs ×4 for the square channels) keeps CH3’s pitch range practical. Because CH3 steps through 32 positions per period cycle instead of 8, using ×4 would place all its pitches an octave lower than CH1/CH2 for the same register value; ×2 closes that gap to exactly one octave.

Reference: Pandocs — Channel 3 registers (NR30–NR34)

The shift table {4, 0, 1, 2} means volume level 0 (shift 4) always produces 0 from any 4-bit value — an elegant mute with no special-case code needed.

Wave RAM Access While Active

On DMG hardware, reading from Wave RAM (0xFF30–0xFF3F) while CH3 is active does not return the byte at the requested address — it returns the byte currently being played (wave_ram[wave_pos / 2]). Writes behave the same way: they target the currently-playing position rather than the requested one. Retriggering CH3 while it is already active also latches that sample byte into position 0 of Wave RAM before resetting the position counter.

Channel 4 — Noise Channel (NR41–NR44)

Channel 4 generates pseudo-random noise using a Linear Feedback Shift Register (LFSR) — a 15-bit register where, on each clock, the output bit is computed from bits 0 and 1 via XOR and fed back into bit 14 (and optionally bit 6 for the shorter 7-bit mode): 

uint8_t xor_bit = (lfsr & 1) ^ ((lfsr >> 1) & 1);
lfsr = (lfsr >> 1) | (xor_bit << 14);
if (lfsr_width == 7)
    lfsr = (lfsr & ~0x40) | (xor_bit << 6); // also feed into bit 6

Output = (~lfsr & 1) ? current_vol : 0 — the channel is high when LFSR bit 0 is 0.

A 15-bit LFSR cycles through 215−1 = 32,767 unique states before repeating. At typical clock rates this spans many frames, so the output appears statistically random — white noise. The 7-bit mode (NR43 bit 3 = 1) constrains the register to 27−1 = 127 states; the short, audible repetition gives it a buzzy, pitched quality useful for metallic percussion and snare-like sounds.

Reference: Pandocs — Channel 4 registers (NR41–NR44)

Frame Sequencer

Rather than running length, envelope, and sweep logic on every CPU cycle, the APU uses a frame sequencer that fires at 512 Hz — once every 8,192 CPU cycles. It steps through 8 positions, each triggering a different subset of functions:

The 8,192-cycle interval is not arbitrary: it matches the rate at which bit 12 of the Game Boy’s internal 16-bit timer counter falls from 1 to 0 — the same counter that drives the DIV register (0xFF04). Reusing that signal costs no extra hardware. The result is 4,194,304 / 8,192 = 512 Hz. The 8-step counter means one full sequencer cycle takes 65,536 cycles (≥15.6 ms).

  • Length counter — clocked at 256 Hz (steps 0, 2, 4, 6)
  • Frequency sweep — clocked at 128 Hz (steps 2 and 6)
  • Volume envelope — clocked at 64 Hz (step 7 only)
switch (frame_seq_counter) {
    case 0: clock_length();                    break;
    case 2: clock_length(); clock_sweep();     break;
    case 4: clock_length();                    break;
    case 6: clock_length(); clock_sweep();     break;
    case 7: clock_envelope();                  break;
}
frame_seq_counter = (frame_seq_counter + 1) % 8;

Reference: Pandocs — Audio (Frame Sequencer timing)

Volume Envelope

The envelope system gives channels a time-varying volume — fading in or out over a configurable duration. It applies to CH1, CH2, and CH4. Three fields in NR12/NR22/NR42 control it:

BitsFieldMeaning
7–4Initial volumeVolume (0–15) when the channel triggers
3Direction0 = fade out (−1), 1 = fade in (+1)
2–0PaceEnvelope ticks between each volume step; 0 = frozen

At each envelope clock (step 7, ~64 Hz):

  1. If env_pace == 0, return immediately (volume frozen)
  2. Decrement the internal counter; if it reaches 0, reload from env_pace
  3. If env_add && current_vol < 15: increment volume
  4. If !env_add && current_vol > 0: decrement volume
void Envelope::clock_envelope() {
    if (env_pace == 0) return; // frozen
    if (--env_counter == 0) {
        env_counter = env_pace;
        if (env_add && current_vol < 15) current_vol++;
        else if (!env_add && current_vol > 0) current_vol--;
    }
}

The bounds check (< 15 / > 0) acts as the clamp — the volume simply stops changing when it reaches the limit.

Reference: Pandocs — Volume Envelope (NR12 / NR22 / NR42)

Frequency Sweep (CH1 only)

The sweep unit periodically shifts Channel 1's frequency up or down, producing pitch glide effects. NR10 (0xFF10) controls three fields:

BitsFieldMeaning
6–4PaceSweep ticks between steps; 0 = timer reloads but no update
3Direction0 = increase frequency (pitch up), 1 = decrease (pitch down)
2–0Step (shift)Right-shift amount for the delta calculation

On each sweep clock (steps 2 and 6, ~128 Hz):

  1. Decrement sweep_counter; if still > 0, return early
  2. Reload: sweep_counter = (sweep_pace == 0) ? 8 : sweep_pace
  3. If !sweep_enabled || sweep_pace == 0: stop (timer reloaded, no frequency change)
  4. If sweep_negate, record that a negate calculation has occurred
  5. Compute delta = shadow_period >> sweep_step
  6. Compute new_freq = shadow_period + (sweep_negate ? -delta : +delta)
  7. If new_freq >= 2048: disable CH1 (overflow — silence the channel)
  8. If sweep_step != 0: write back to both shadow_period and period_value; then perform a second overflow check on the updated shadow period — if that also overflows, disable CH1 immediately

A negate-mode tracking flag (negate_was_used) ensures that once Channel 1 has computed a frequency in negate mode, subsequently clearing the negate bit in NR10 will immediately disable the channel — a DMG hardware quirk required for correct sweep behaviour.

When sweep_step = 0, right-shifting by zero is the identity, so delta = shadow_period — the full value. In negate mode this gives shadow − shadow = 0 (never overflows); in positive mode it gives shadow + shadow = 2×shadow, which overflows and disables CH1 when shadow ≥ 1024. The hardware always runs the overflow check but never writes the result back — which is why sweep_step = 0 means “check only, no frequency update.”

The shadow period is a copy of the period register initialised on each CH1 trigger. The sweep algorithm operates on it, ensuring the actual period register only changes when a sweep step commits a valid new frequency. 

void SquareChannelWithSweep::clock_sweep() {
    if (--sweep_counter > 0) return;
    sweep_counter = (sweep_pace == 0) ? SWEEP_TIMER_DEFAULT : sweep_pace;
    if (!sweep_enabled || sweep_pace == 0) return;

    if (sweep_negate) negate_was_used = true; // track for negate-exit disable

    int delta    = shadow_period >> sweep_step;
    int new_freq = shadow_period + (sweep_negate ? -delta : +delta);

    if (new_freq >= APU_PERIOD_MAX) { // overflow → silence
        enabled       = false;
        sweep_enabled = false;
        return;
    }
    if (sweep_step > 0) { // step=0 checks overflow but keeps original frequency
        shadow_period = (uint16_t)new_freq;
        period_value  = (uint16_t)new_freq;
        // second overflow check after write-back
        int delta2 = shadow_period >> sweep_step;
        int next2  = shadow_period + (sweep_negate ? -delta2 : +delta2);
        if (next2 >= APU_PERIOD_MAX) { enabled = false; sweep_enabled = false; }
    }
}

Reference: Pandocs — Frequency Sweep (NR10)

Mixing — NR51 Panning and NR50 Master Volume

Each sample, all four channels are routed to left and right outputs based on NR51's 8 bits — one bit per (channel × side):

Bit76543210
Side← Left →← Right →
ChannelCH4CH3CH2CH1CH4CH3CH2CH1
int left  = ((nr51 & 0x10) ? ch1 : 0) + ((nr51 & 0x20) ? ch2 : 0)
           + ((nr51 & 0x40) ? ch3 : 0) + ((nr51 & 0x80) ? ch4 : 0);
int right = ((nr51 & 0x01) ? ch1 : 0) + ((nr51 & 0x02) ? ch2 : 0)
           + ((nr51 & 0x04) ? ch3 : 0) + ((nr51 & 0x08) ? ch4 : 0);

Then NR50 applies a master volume multiplier to each side independently: 

int left_vol  = ((nr50 >> 4) & 7) + 1; // bits 6-4, range 1–8
int right_vol = (nr50 & 7) + 1;         // bits 2-0, range 1–8

sample_buffer.push_back((int16_t)(left  * left_vol  * AUDIO_SAMPLE_SCALING));
sample_buffer.push_back((int16_t)(right * right_vol * AUDIO_SAMPLE_SCALING));

The AUDIO_SAMPLE_SCALING constant maps the maximum possible mixed sum to just below INT16_MAX, preventing integer overflow. The maximum per side is 4 channels × 15 (max envelope volume) × 8 (max NR50 multiplier) = 480, so 32,767 / 480 ≈ 68. Rounding down keeps the peak safely within the 16-bit ceiling; the tiny headroom (≈0.4%) is inaudible.

Reference: Pandocs — NR51 Sound Panning / NR50 Master Volume

SDL Audio Output

The emulator produces audio at exactly the rate the Game Boy hardware would — driven purely by the CPU cycle counter, not by wall-clock time.

Inside apu.step(cycles, memory), a uint32_t sample_counter accumulates CPU cycles scaled by the sample rate. Each time it exceeds CPU_FREQUENCY (4,194,304), one stereo sample pair is emitted: 

sample_counter += cycles * AUDIO_SAMPLE_RATE; // AUDIO_SAMPLE_RATE = 44100
while (sample_counter >= CPU_FREQUENCY) {
    sample_counter -= CPU_FREQUENCY;
    // mix all four channels → push left, right int16 to sample_buffer
}

This produces 44100 / 59.7 ≈ 738 stereo pairs per frame. After each step_frame() call, the main loop hands the buffer to SDL: 

SDL_PutAudioStreamData(audio_stream,
    gameboy.apu.sample_buffer.data(),
    gameboy.apu.sample_buffer.size() * sizeof(int16_t));
gameboy.apu.sample_buffer.clear();

Frame Pacing

Frame rate is enforced by std::this_thread::sleep_until targeting exactly 59.7 Hz. A clamp prevents the timer from falling too far behind after slow frames, which would otherwise cause a burst of frames (and audio samples) with no sleep between them: 

next_frame += frame_duration;
auto now = std::chrono::steady_clock::now();
if (next_frame < now) next_frame = now; // clamp — discard deficit, don't catch up
std::this_thread::sleep_until(next_frame);

Two frames of silence are pre-filled into the SDL stream before the main loop begins, giving the audio device a ~33 ms headroom buffer to draw from during any frame spikes.

A Bug Worth Noting — The LCD-Off Spike

During testing, severe audio hitches appeared at specific game events: entering buildings, starting battles, and loading saves in Pokémon. The audio stream showed genuine underruns at those moments. Increasing the pre-fill buffer helped but did not fully eliminate them.

Investigation revealed the cause was in the PPU, not the audio system. When the LCD is disabled (LCDC bit 7 = 0 — something the game does during screen transitions), ppu.step() was calling update_rgba_buffer() and setting frame_ready = true on every single call: 

// BEFORE (bug): called on every ppu.step() while LCD is off
if (!(lcdc & LCDC_ENABLE)) {
    framebuffer.fill(0);
    update_rgba_buffer(); // iterates 160×144 = 23,040 pixels
    frame_ready = true;
    return;
}

ppu.step() is called once per CPU instruction. With a minimum of 4 cycles per instruction and 70,224 cycles per frame, this function could be called up to 17,556 times while the LCD is off. Each call performs 23,040 pixel-copy iterations: 17,556 × 23,040 ≈ 400 million iterations per frame. Even on fast hardware, this caused ~100 ms frame spikes — and those spikes drained the audio buffer.

The fix: track whether the LCD was already off with a bool lcd_off in the PPU struct, and perform the expensive work only once — on the transition from on to off: 

// AFTER (fix): expensive work runs only once per LCD-off transition
if (!(lcdc & LCDC_ENABLE)) {
    if (!lcd_off) {
        lcd_off = true;
        mode = PPUMode::OAMSearch;
        mode_cycles = 0;
        scanline = 0;
        window_line_counter = 0;
        memory.write(IO_LY, 0);
        framebuffer.fill(0);
        update_rgba_buffer();
        frame_ready = true;
    }
    return;
}
lcd_off = false; // LCD is back on — next step resumes normal rendering

After this fix, frame times during screen transitions dropped from ~100 ms back to the normal ~2 ms, eliminating the audio underruns entirely.
